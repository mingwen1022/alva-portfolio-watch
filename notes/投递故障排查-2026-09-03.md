# 告警投递中断排查 · 2026-09-03

**结论：平台侧。** 我们这一端到 `append` 全绿，断点在 `append` 之后、
投递记录之前 —— 那一段在 Alva 手里。

起因是用户问「刚才八点多比特币暴涨，为什么没提醒」。查下来是两件不同的事：
BTC 按规则确实不该响（量能腿不到线的一半），而 **DOGE 响了却没送到**。

---

## 一、被证实的失败范围

⚠️ **先订正一个说重了的判断。** 我最初说「09-01 18:30 之后全线停投」——
那是拿「没有投递记录」当「投递失败」。查去重表 `pushedBars:portfolio-watch` 发现
**09-02 一条记录都没有**：那天本来就没有东西该推。

```
被证实的失败只有 09-03 一天，三次，全部零投递：
  16:15  DOGE PV5 首次触发
  17:30  DOGE PV5 补推（我撕掉去重记录后）
  18:00  BTC US2 受控测试
```

**「没送出去」和「本来就没东西送」在投递记录里长得一模一样。**
判断中断范围必须拿「我们发出过什么」去对，不能只看「收到过什么」。

## 二、证据链

| 环节 | 结果 | 怎么查的 |

| cronjob 在跑 | ✅ run_count 1111，最近一轮 18:00:52Z | `alva deploy list` |

代码这一侧是关键：`producer-intraday.js` 最后一次改动是 **08-27 17:18**，
而 **08-28 · 08-30 · 08-31 · 09-01 四次成功投递全在那之后**。
最后一次成功与首次失败之间，我们一个字都没动过（09-02 无人在线，无任何上传）。

**422 internal system error**；`automation delivery` 拒收自己文档里标为必填的 `--id`。

## 三、决定性测试怎么做

光看「没收到」永远分不清是平台坏了还是我们没发。要分清，只能**走完整生产路径真推一次**。

⚠️ **手工 `alva run` 测不了投递。** 它会 append、会标记去重，但**不投递**
（`scripts/_clearkv.js` 的注释记着这条）。所以测试必须由绑定的 cronjob 跑。

做法：把一条用户线临时压到必然成立的位置，等下一轮 15 分钟任务自然跑，
然后比对 `meta.lastPush` 与 `alva alert history`。

**载荷要挑和最后一次成功投递同形的那种。** 本次用 US2 用户线，
因为 09-01 最后一次成功正是「MSTR reached a line you set」——
同样的形状、同样的路径，现在不通就只剩一种解释。

```
18:00:52Z  meta.lastPush = {"at":"2026-09-03T18:00:52.762Z","count":1,
                            "ids":["2026-09-03:BTC:US2"]}
           alva alert history 最新仍是 2026-09-01T18:30:17Z
```

### 测试的副作用必须清理

⚠️ **finding 的 id 里不含线值。** 测试用的 79,000 和用户真正要的 86,000
共用同一个 id `2026-09-03:BTC:US2`。测试触发后那个 id 进了去重表，
**不撕掉的话，当天 BTC 真涨到 86,000 会被当成「已推过」直接跳掉。**

测试完必须做两件事：把线改回原值 · 撕掉去重表里那条 id。
**测试不能吃掉一条真告警。**

## 四、我们自己的缺陷：这次失败从我们这侧完全看不出来

`ctx.self.ts("alerts","events")` 上**只有 `append`，没有查询也没有回执**
（探测确认：原型上只有 `constructor` 和 `append`）。所以「确认送达再标记为已推」
在这个 API 上做不到。

而代码原来是无条件标记：

```js
await ctx.self.ts("alerts", "events").append([...]);   // 成功 resolve
for (const f of fresh) seen[f.id] = 1;                 // 标记落下
```

append 成功、标记落下、手机上什么都没有 —— **而从我们这一侧完全看不出异常**。
后果是即使投递恢复，那几条也永远不会补推。

做不到确认，就留痕。本次新增：

1. **`meta.lastPush = { at, count, ids }`** —— 记下这一轮发了什么。
   它与 `alva alert history` 可以逐条对账，两边对不上就是投递侧的问题，
   而不再是「不知道发生了什么」。上线 15 分钟就派上用场。
2. 去重表的值从 `1` 改成**时间戳** —— 存 `1` 只能回答「标过没有」，
   回答不了「哪一轮标的」。
3. 契约 `product/output-schema.md` 补 `meta.lastPush` 一节。
4. 冒烟加断言：推了就必须在 `meta.lastPush` 里记下且条数与 id 数对得上。

⚠️ **投递坏着的这段时间，每一条新告警都会被标成「已推」然后永久吞掉。**
`meta.lastPush` 至少让这些丢失是**可清点的** —— 恢复后能从它里面挑出没到的，
但补推得手工来。
